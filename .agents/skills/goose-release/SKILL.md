# 鹅鸭杀项目发布

## 版本号是每次推送的必做项

- 用户要求：每次推送新的代码修订，都必须写入新的版本号。开发期间可以重复构建尚未推送的同一版本；网络失败后的同一提交重试不另加版本。
- 发布前先读取目标仓库 GitHub 的最新主分支、最新发布、对应 Alpha 系列标签，以及当前远程分支的版本。不能只看本地 `gradle.properties`，也不能只看 GitHub main；正式发布可能来自尚未合并的功能分支。
- 沿当前活跃版本系列递增，使用大于该系列已发布、已推送和当前本地测试版本的编号。例如远程 Alpha0.19、本地测试 Alpha0.21，则本次新发布批次用 Alpha0.22。不要用字符串排序比较 Alpha0.9 与 Alpha0.19，也不要混入较早的其他发布系列。
- 模组以各自 `gradle.properties` 的 `mod_version` 为准，同步修改当前发布说明。不同仓库独立递增，不要求 GooseTools 与 GooseThings 的后缀相同。
- 数据包没有 `mod_version` 时，在本次发布说明记录配套模组版本及验证范围；不要将 Minecraft 版本、`pack_format`、商城目录版本或协议号当作发布计数器。仅在真实兼容性变化需要时修改协议。
- 如果无法验证远程最新状态，继续整理和验证本地代码，但先解决查询问题再发布，不能凭记忆猜下一个编号。

## 合入与验证

- 发布前获取目标主分支，并在功能分支中整合更新。保留他人已经修复的逻辑，不把旧文件整份覆盖到最新版本。检查交集文件以及合并后的实际行为。
- 数据包同时维护 `datapack` 与 `sources/full-datapack`。保留服务器输入中有意存在的差异；不要通过整目录覆盖来强行一致。
- 对最终提交运行与改动相关的验证，并以新版本号构建模组。区分已验证的代码、已生成的包和实际安装的包；不能把旧版本测试包说成新版本已经部署。
- 只提交授权范围内的源码、测试和文档。机器路径配置、测试存档、备份、日志、生成的 JAR、临时凭据和其他无关产物不进入提交。

## 推送与合并请求

- 同一发布批次中的仓库分别提交到功能分支，并向各自正式仓库的目标分支创建 PR；没有正式仓库写权限时使用已有 fork。未经明确要求不直接合并 main、不重写远程历史、不发布正式 Release。
- PR 说明写清问题、行为变化、配套版本、验证结果及依赖的其他 PR。推送前再次确认版本未被其他开发者占用。
- 推送成功后核对远程提交和 PR 状态，报告准确的版本号及 PR 链接。已有相同提交时视为成功，不重复创建 PR。
